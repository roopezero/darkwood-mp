# Developing DarkwoodMP

- **Requirements:** the .NET 8 SDK (a newer SDK also needs the .NET 8 runtime, because the unit tests run on it), and BepInEx installed in the game folder (the build references its DLLs and the game's).
- **Game version:** the mod is built against Darkwood 1.4 (Unity 2021.3.30f1; Steam build 13092424 on Linux). The game's version is stored in `Darkwood_Data/globalgamemanagers` and shows in the save folder's name (`1_4Save`). After a game update, rebuild and run the tests before releasing.
- **Projects:** `src/DarkwoodMP` is the plugin: it reads the game, applies what the core decided, and holds the Harmony patches, the Steam backend and the menus. `src/DarkwoodMP.Core` holds the rules, the network code (`Session`, the messages, `TcpBackend`, the server browser) and small types that don't touch Unity or the game, and ships as a second DLL beside the plugin; both use the same feature folders (`World/Doors`, `Combat/Enemies`, ...). `src/DarkwoodMP.MapTests` holds the in-game map test steps, a second plugin that never ships. `src/DarkwoodMP.Analyzers` holds the build's formatting rules (DW0001 to DW0008). `tests/DarkwoodMP.Core.Tests` holds the core's unit tests (about 7,600, in the same folders as the code they test), and `tests/DarkwoodMP.Analyzers.Tests` the formatting rules' tests. [ARCHITECTURE.md](ARCHITECTURE.md) says how the code is organised.
- **Version:** the mod's version is the `<Version>` in `Directory.Build.props` at the repo's root. Both DLLs get it, and the plugin compiles it into `PluginInfo.Version`.
- **Build:** `dotnet build src/DarkwoodMP -c Release` builds the plugin and the core, and copies both DLLs (`DarkwoodMP.dll` and `DarkwoodMP.Core.dll`) into `<game>/BepInEx/plugins/DarkwoodMP/` and into every client game folder the map tests use. `-p:DeployToGame=false` builds without copying anything. The game folder defaults to Steam's; override it with `-p:GameDir=/path/to/Darkwood`. `dotnet build src/DarkwoodMP.MapTests -c Release` builds the mod too and also copies the map test steps (`DarkwoodMP.MapTests.dll`, a second plugin that does nothing without `--dwmp-test-control`) to the same folders; the in-game tests need it, and `tools/run-test.sh` stops if it isn't in the game folder. `./pack.sh` builds the three release zips, and stops if a zip lacks either DLL or holds the map tests.
- **Style rules:** `.editorconfig` and the analyzer check the formatting rules in [ARCHITECTURE.md](ARCHITECTURE.md) on every build. They are errors in every project, so a build with a finding fails. `-p:RunAnalyzers=false -p:EnforceCodeStyleInBuild=false` skips the checks for a quicker build while trying something out.
- **Release check:** `dotnet build src/DarkwoodMP -c Release --no-incremental -warnaserror` fails on any compiler warning. `--no-incremental` is needed: a second build skips the compiler and shows no warnings at all.
- **Unit tests:** `dotnet test tests/DarkwoodMP.Core.Tests -c Release --blame-hang-timeout 60s --blame-hang-dump-type none`. They need neither the game nor a display. Besides the rules, they run the network in one process: the session's handshake, refusals and relaying over an in-memory backend, the info query's bytes, and TCP framing over 127.0.0.1 (the tests open local ports). `dotnet test tests/DarkwoodMP.Analyzers.Tests` with the same options runs the formatting rules on small pieces of code, a case that fires and one that stays quiet for each rule; run it after changing `src/DarkwoodMP.Analyzers`.
- **In-game tests:** `tools/run-test.sh <test>...` first runs `tools/check-file-ends.sh` (every text file ends with one line break) and the core's unit tests, and stops there if either fails. It then runs the real game against scripted Python players (`tools/tests/`), `tools/run-test.sh all` for every test. One game runs the whole list: the script starts it with `--dwmp-test-control PORT` and sends it each test's title (shown along the top of the screen, "Test (3/17): host-world - ..."), a reset back to the main menu, and the test's arguments. It plays a copy of your save, and checks after each test that your saves are unchanged and that there were no new exceptions. `tools/run-test.sh map` runs two real games instead: the host plays the test world (a copy of your save), the client is a second copy of the game made by `tools/setup-client-game.sh` in `~/.cache/darkwood-mp/client-game` with its own home folder, and they join over Direct on 127.0.0.1. Scripted steps (`tools/tests/map_scenario*.py`, `src/DarkwoodMP.MapTests/World/MapScenario*.cs`) have each player do one of everything that's shared and the reported bugs' cases; then both games dump their shared world (`Testing/StateDump.cs`, its sections in `Testing/DumpSections.cs`) and `tools/tests/mapcompare.py` checks the two agree. At the end every game goes back to its main menu before its exceptions are counted, so what a world throws as it is torn down counts too (in `map4`, every client game's). The map test is split into parts that each run alone, in any order and with a fresh world each (`tools/run-test.sh map:ui map:knock`, `maps` for every part, `--list` for all of them, `--plan` to see what would run); a results table at the end gives each one's result, time, first failure and the command that reruns it. [MULTIPLAYER_TESTING_GUIDE.md](MULTIPLAYER_TESTING_GUIDE.md) says which part covers what and how long each takes (`maps` about 80 minutes).
- **What the test scripts refuse:** `tools/run-test.sh` and `tools/setup-client-game.sh` don't run as root. `run-test.sh` won't start while a Darkwood it didn't start is running (quit your own game first), and copies the saves' contents (never a link to them) into `$WORK/saves-backup` and `$WORK/sandbox`. If a test changed your saves, it writes `$WORK/SAVES-CHANGED` and every later run refuses to start, so the backup of the saves from before that run is kept until you have checked them and deleted the marker. The `options` test changes your real game settings: the script copies Unity's `prefs` file before it and, with the game stopped, puts it back if it changed. `setup-client-game.sh` refuses a `CLIENT_GAME` that is the game folder, inside it or around it, and a `CLIENT_HOME` that is your home. Every recursive delete in the shell tools goes through `safe_rm ROOT PATH...` in `tools/lib.sh`, which deletes only inside ROOT and refuses an empty path, `/`, your home, `..` escapes and paths through links.
- **Launch arguments** (used by the tests, also handy for always-on hosts):
  - `--dwmp-host` hosts Direct at once, and `--dwmp-join host:port` joins once the menu is up.
  - `--dwmp-continue N` loads your profile N, and `--dwmp-sandbox DIR` plays a copy of saves in DIR.
  - `--dwmp-password P` hosts with that password this time only (your setting is untouched).
  - `--dwmp-upnp-test HOST:PORT` makes Direct hosting open its port on a scripted router there (`tools/tests/fakerouter.py`: its UPnP description at `http://HOST:PORT/rootDesc.xml`, NAT-PMP on UDP HOST:PORT) instead of discovering the real one. A game started for the tests (any `--dwmp-test...` argument, the test world or test control) never asks the real router.
  - Test hooks: `--dwmp-test-start-window` (opens the Start Game window; with `--dwmp-sandbox DIR` on a copy of the saves, `--dwmp-shots DIR` screenshots, `--dwmp-start N|new` then starts slot N or a new game, `--dwmp-start-host direct|steam` hosting it, `--dwmp-start-name NAME` naming it, `--dwmp-start-epilogue standing|burned` choosing *Start at: Epilogue* with the Talking Tree so; `tools/run-test.sh map:epilogue_start` starts such a game, which goes into the epilogue by itself, has a client join it there and plays the epilogue through; `map:epilogue_late` has the host play on alone to the flat before the client joins, which must land in the flat; a module's `PRE_JOIN` steps run in the host's new game before the client joins), `--dwmp-dummy`, `--dwmp-spawn TYPE`, `--dwmp-test-world`, `--dwmp-test-save N`, `--dwmp-test-death`, `--dwmp-test-reload N`, `--dwmp-test-menu N`, `--dwmp-test-client-actions`, `--dwmp-test-client-menu` (as a client, back to the main menu once the character has come, then join the `--dwmp-join` address again), `--dwmp-test-blast`, `--dwmp-steam-test`, `--dwmp-test-presence` (logs the Steam presence text every 5 s, even without Steam), `--dwmp-shots DIR`, `--dwmp-test-control PORT`, `--dwmp-test-menu-entry`, `--dwmp-solo-test DIR` (playing alone, with `--dwmp-continue N --dwmp-sandbox DIR`: the pause menu over the world, the Skills panel and a point spent, two more spent one after another with the real mouse when ydotool and its socket `/tmp/.ydotool_socket` are there (Linux), skill resets at the stove outside and in the morning, and a level taken at the stove, with screenshots), `--dwmp-screen WxH` (a window that size, for checking other screen shapes; with `--dwmp-shots DIR`, screenshots), `--dwmp-testworld` (starts the test world from the main menu; with `--dwmp-reset`, from a fresh copy; with `--dwmp-shots DIR`, screenshots of the area once it's built), `--dwmp-dump-prefabs` (once in a world, logs every prefab the save system knows, name and path), `--dwmp-test-tooltips DIR` (once in a world, writes `DIR/tooltips_dump.json`, the items' fields and recipes and the map's elements that `tools/gen_tooltips.py` turns into `World/Texts/Tooltips.tsv`, then checks that every item and map location has a description; the `tooltips` test).
  - Logging: `--dwmp-debug-world` (with the requests and verdicts), `--dwmp-debug-threat`.
  - Speed: `--dwmp-profile-load` times the game's loading code and logs the slowest parts; `--dwmp-verify-load` checks the faster grid lookup against the game's own (see `World/Loading/LoadSpeed.cs`); `--dwmp-profile-mod` logs what each part of the mod's per-frame work costs, every 10 seconds.

## Test world

For trying out what's shared without touching your own saves. It's a tool for testing the mod, so the panel only shows it when the game was started with a `--dwmp-test...` argument (as `tools/run-test.sh` does) or `--dwmp-testworld`. Then, in the main menu, the panel's *Test world* section has *Make and start a test world* (later *Start the test world*) and *Reset it*. It copies your saves into `BepInEx/cache/DarkwoodMP/testworld` and plays that copy through the same save redirect a joiner uses, so your own saves are never written; *Reset it* makes a fresh copy. The first time it loads, the game builds a test area of 21 labelled things around your character, out of the game's own pieces: containers and crates (one locked), a workbench, furniture to drag, a generator with two lamps on it, the saw, candles, a radio, a stove, traps, an exploding barrel, a gas bottle, broken glass, a larva egg, a patch of infection and the night trader. Each has a label over it saying what to try. Doors and windows aren't separate pieces in the game, so use the hideout's own. You get a kit (gasoline, matches, molotovs, flares, a torch, a lantern, a flashlight, a pitchfork, a shotgun and shells, planks and nails, traps, bandages), and in the world the host's panel can give it again, set the clock to dawn, noon, dusk or night, and spawn enemies near you (dogs, chompers, a centipede, a kamikaze, a human spider). Save the world after the area is built: if none of it is there on the next load, it's built again. Host it and friends join it as any hosted world. It has been built and checked by the host only, not yet played by two people, and some things can land inside walls.

## Clips for the docs

The side-by-side clips in `docs/media/` (in the README and the guide) are recorded from the two-game map test. Each `tools/tests/map_scenario_showcase_NAME.py` (`combat`, `world`, `share`, `join`; `scout` records a second at points around the test area, for finding spots) is a battery kept out of `maps` that plays a scene and has both games record their screens. They have no verdict of their own beyond the usual dumps:

```
CLIP_DIR=/tmp/clips tools/run-test.sh map:showcase_world
tools/make-clips.py /tmp/clips/drag docs/media/drag.webp --zoom 2.5
```

The map test steps that do it are in `src/DarkwoodMP.MapTests/World/MapScenarioClips.cs`:
- `rec-start DIR [FPS [WIDTH]]` and `rec-stop` save each game's screen as JPG frames, named by the machine's clock, into `DIR/host` and `DIR/c1`.
- `clip-overlays off|on` hides the test world's labels and the test's title.
- `clip-face DX DZ|off` points a player's mouse at a spot, so it faces there.
- `clip-watch [DIST [SIDE]]` walks up to the other player and keeps facing them.
- `clip-panel` opens the Multiplayer window from the pause menu.
- `clip-join ADDRESS` takes a client back to the main menu and joins from *Join Game*'s server browser.

`tools/make-clips.py` pairs the two games' frames by time, puts them side by side with "Host" and "Friend" captions and writes an animated WebP of at most 2 MB. Its `--zoom`, `--focus` and `--cut` options crop it and choose the seconds to keep, and `--preview` writes a contact sheet of one pair a second for choosing them. It needs Pillow, for example in a virtual environment (`python3 -m venv VENV && VENV/bin/pip install pillow`).

Before recording, set the host game's `PlayerName` to something neutral, such as `Host`: the host's name shows in the friend's game and in the Multiplayer window. Check the frames for names and addresses before committing a clip.

## Reading the game's code

`ilspycmd -p -o <dir> <game>/Darkwood_Data/Managed/Assembly-CSharp.dll`, run with `DOTNET_ROLL_FORWARD=Major` for ilspycmd 8.2. Never commit decompiled code.

## Claude Code

`CLAUDE.md` has the project's rules, and `.claude/skills/` has skills for testing, adding a shared feature, reading the game's code, and releasing.

`container/box` runs Claude Code on the repo inside a rootless podman container, so what it runs reaches only the repo, the box's own home, this project's Claude memory and the game folder. Its default mode builds and runs the unit tests; `container/box --game` adds the display, the GPU, a writable game folder and a copy of the saves, for the in-game tests. `container/box remote` runs Remote Control in the box, so it can be used from claude.ai/code. [container/README.md](../container/README.md) has the details.
